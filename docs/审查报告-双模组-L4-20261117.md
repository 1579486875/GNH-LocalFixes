### ⑧ `InitLoadFolders` 反编译：1.6 下到底加载哪些目录（2026-11-17 新增）

模板 §B.11 说这个方法有三处最容易读错。反编译 1.7.5011.24 的
`Verse.ModContentPack.InitLoadFolders`，关键分支如下：

```csharp
if (modWithIdentifier?.loadFolders != null && modWithIdentifier.loadFolders.DefinedVersions().Count > 0)
{
    var list = modWithIdentifier.LoadFoldersForVersion(VersionControl.CurrentVersionString);
    if (list != null && list.Count > 0) { AddFolders(list); return; }      // ① 精确命中

    // ② 退而求其次：版本号 <= 当前版本 里最大的那个
    var text = (from x in DefinedVersions()
                where x != "default" && x.Contains(".") && VersionFromString(x) <= CurrentVersion
                orderby x descending select x).FirstOrDefault();
    if (text != null) { var l2 = LoadFoldersForVersion(text); if (l2 != null) { AddFolders(l2); return; } }

    // ③ 最后才用 default
    var l3 = LoadFoldersForVersion("default");
    if (l3 != null) { AddFolders(l3); return; }
}

void AddFolders(List<LoadFolder> folders)
{
    // ★ 倒序添加 —— 所以 foldersToLoadDescendingOrder 是「后面的先加载」
    for (int i = folders.Count - 1; i >= 0; i--)
        if (folders[i].ShouldLoad)
            foldersToLoadDescendingOrder.Add(Path.Combine(RootDir, folders[i].folderName));
}
```

**对 NMM 的意义**：

| 环境 | 命中分支 | 实际加载 |
|---|---|---|
| 1.6 | ②（`<v1.6><li>/</li></v1.6>`） | **只有根目录** |
| 1.7 | ①（`<v1.7><li>/</li><li>v1.7</li></v1.7>`） | 根目录 + `v1.7/`，**且 `v1.7` 先加载、根目录后加载** |

`AddFolders` 的**倒序**意味着列表里越靠后的目录**越先加载** —— 这正是
`<v1.7><li>/</li><li>v1.7</li></v1.7>` 把 `v1.7` 写在后面能生效的原因。

**所以「根目录每个键都要对 1.6 负责」不是建议，是此方法的直接推论**（对应 ① 的 11,283 键 0 悬空）。

### ⑫ `MayRequire` 是**大小写不敏感**的（反编译实证）

GNH 的 22 个补丁里**一个 `PatchOperationFindMod` 都没用** —— 注释写得很清楚：

> `PatchOperationFindMod` 那个是按 `ModMetaData.Name`（显示名）匹配的
> （已反编译确认：`ModLister.HasActiveModWithName` 里是 `mod.Name == name`），
> **显示名一改守卫就失效，不如不用**。

全部改用 `MayRequire="<packageId>"`。而 `MayRequire` 最终走的是：

```csharp
// Verse.ModsConfig
public static bool IsActive(string id) => activeModsHashSet.Contains(id.ToLower());
```

**先 `ToLower()` 再查 HashSet** → **大小写不敏感**。

这条很关键：`Patches/` 里写的是 `MayRequire="solaris.ratkinracemod"`，
而模组实际的 `packageId` 是 **`Solaris.RatkinRaceMod`** —— 大小写完全不同，
靠这条不敏感才成立。如果把 `MayRequire` 改成大小写敏感的比较，那个补丁会**静默失效**。

5 个 `MayRequire` 值逐个核对：

|---|---|---|
| `ASEL.MonolynRace` | 一致 | 工坊 3742031864 |
| `Ludeon.RimWorld.Ideology` | 一致 | DLC（`Data/Ideology`） |
| `RI.RimImmortal.Living` | 一致 | 工坊 3326145525 |
| `eltoro.rjw.menstruation.fluids` | 一致 | 本地 `RJW-玩法-月经周期-…` |
| **`solaris.ratkinracemod`** | **`Solaris.RatkinRaceMod`** | 工坊 1578693166 ← **靠不敏感匹配** |

### ⑯ 两个模组的补丁安装都是**幂等**的（模板 §0 硬要求）

模板 §0 把这条列成事故教训：`Mod` 子类构造**不受 CLR 保证只跑一次** ——
构造函数抛异常时那条记录不会写进 `runningModClasses`，之后会被**重复构造**；
而 Harmony 补丁是**叠加**的，失败后的重试会在同一方法上再套一层 prefix。

**GNH 的做法：`lock` + `HashSet<Type>`**

```csharp
private static readonly HashSet<Type> installedPatchClasses = new HashSet<Type>();

private static bool InstallPatchClass(Type type)
{
    lock (installedPatchClasses)
    {
        if (installedPatchClasses.Contains(type)) return false;   // ← 幂等守卫
        ...
        // 玩家把这一项关掉了就跳过，但**不写 HashSet** ——
        // 这样中途把开关打开、下一次（切语言 / 热重载）触发本方法时能立刻装上
```

**`lock` 保证线程安全**（`InstallAllPatchClasses` 可能被多处调用），
**`HashSet` 保证不重复装**，**跳过时不记名**保证「开了就能装」。

而且它**刻意不用 `Harmony.PatchAll`** —— 注释写得很清楚：`PatchAll` 遇到任何一个补丁类
出错就整体中止，后面排队的类全不装；逐个 `TryInstall` 才能「一个坏了不拖累其他」。

**NMM 的做法：CLR 保证 + 静态标志双保险**

```csharp
static OwnListInjector()
{
    if (ran) return;                              // ← 第二重保险
    if (!ForceLegacy && HasKeyedPath()) return;   // 1.7 有 Keyed 路径就跳过（且不设 ran）
    ran = true;
    try { Run(); } ...
}
```

`[StaticConstructorOnStartup]` 本身由 CLR 保证只执行一次；`ran` 是「万一将来被改成
非静态构造」的兜底。**`HasKeyedPath()` 为真时不设 `ran = true`** —— 这样如果环境后面变了，
下次还能再跑。

### ⑰ `refs\Assembly-CSharp.dll` 钉在 1.6 是**有意的**（本轮差点改错）

csproj 里原本写着「每次游戏本体更新后，先重新同步 `refs\`，再编译」。
本轮实测发现 `refs/` 里是 **1.6** 的程序集、而游戏是 **1.7** —— 按那句话看像是「过期没同步」。

**逐哈希比对后结论相反**：

| 文件 | FileVersion | SHA256 前 8 | 大小 |
|---|---|---|---|
| `refs\Assembly-CSharp.dll` | **1.6.9676.17735** | `5cf1b5be` | 15,777,280 |
| `D:\RimWorld-1.6\…\Managed\Assembly-CSharp.dll` | **1.6.9676.17735** | `5cf1b5be` | 15,777,280 |
| `D:\steam\…\RimWorld\Assembly-CSharp.dll` | 1.7.9816.739 | `7fbce7a5` | 15,637,504 |

**前两者逐哈希一致，第三个故意不同。**

**为什么这样对**：本模组同时支持 1.6 与 1.7。用 **1.6 的程序集**编译，能保证

反过来若拿 1.7 的编译，一旦用到 1.7 新增 API，1.6 玩家那边就是 `MissingMethodException`

所以 csproj 那段是**单版本开发的通用建议**，不适用于本工程。
已补 1,517 字节长注释写清，并给出升级前提（先确认新 API 在 1.6 里也存在、两边都编一遍）。

新闸门 `tools/check-refs-baseline.py` 判据：**refs 的 SHA256 == 1.6 引擎副本的 SHA256**。
它防的是「有人顺手跑了 `tools/sync-refs.ps1`」—— 那个按 `$RimWorldDir`（默认 1.7 主安装）同步，
一跑就把 refs 升到 1.7，**静默破坏 1.6 兼容**，而且编译照样通过，问题只在 1.6 玩家那边出现。
还会额外报一种状态：若 refs 与 **1.7** 的哈希相同，直接判失败（说明已被同步过）。

> 这是本轮**第二条「文档该改、行为不该改」**的结论（第一条是 ⑮ 技术说明的历史归档）。

### ⑱ 闸门的「可移植性」：4 道依赖本机环境的闸门都有 skip 分支

RimCrow 数据库 / 两个部署目录）。按失败处理会让换台机器或别人的 CI 永远红 ——

### ⑳ 【44】实机验证：隔离了 **2 个第三方**的坏补丁类，我们自己的全装上

[ATC] Native startup injection deferred: no unchanged verified baseline.
[AutoTranslationCore] Def injection results: submitted=0, succeeded=0, failed=0, skipped=0.

三个关键点：
