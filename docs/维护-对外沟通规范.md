# 维护时的对外沟通规范

> 适用于 GNH-LocalFixes 与 NudityMattersMoreOpinions-CN 两个仓库。
> 建立日期：2026-11-19（用户明确要求：「每次维护的时候都要看一下有没有人提交问题」）。

## 一、开工先查，别等收工

**每次开始维护，第一件事是查有没有人提问题。**

```bash
gh issue list --repo 1579486875/GNH-LocalFixes --state all
gh pr    list --repo 1579486875/GNH-LocalFixes --state all
gh issue list --repo 1579486875/NudityMattersMoreOpinions-CN --state all
gh pr    list --repo 1579486875/NudityMattersMoreOpinions-CN --state all
```

另外工坊评论区也要扫一眼 —— 那边的反馈不会进 GitHub，但往往比 issue 更早暴露问题。

**为什么放在开工而不是收工**：issue 里常常藏着**新版本才有的崩溃**。先看一眼，
这一轮的修改方向可能就要变；等收工才看，等于白做一轮。

## 二、逐条处理，四种情况

| 情况 | 做法 |
|---|---|
| **能修** | 修掉 → 在 issue 里说明改了什么 → 回复 + 关闭 |
| **已经解决的**（比如新版本已修） | 回复说明从哪个版本起好的 → 关闭 |
| **不是本模组的问题** | 回复摆数据 / 证据，说清是哪个环节 → 关闭（留一句「有新证据随时重开」） |
| **需要用户回测** | 回复说明要测什么 → **先不关**，等他回；超过两周没动静再关 |

**关闭理由**：查清并给了结论的用 `completed`；确认不打算改的用 `not_planned`。
**不要留着一堆「已回复但开着」的 issue** —— 后来的人会以为问题还没处理。

## 三、语气：耐心、客气、像人写的

### 3.1 三条硬要求

1. **先谢再答**。对方花时间贴日志、附报告，这本身就值得一句谢谢。
2. **拿证据说话，不拿结论压人**。说「你这份报告里我们这项是 64.7 ms」，
   而不是「这不是我们的问题」。
3. **承认自己那边的错**。如果确实是我们的问题，第一句就道歉，别铺垫。

### 3.2 什么算「AI 味」（要避免的写法）

| 别这么写 | 为什么 |
|---|---|
| 首先……其次……最后…… | 三段式排比，人说话不会这么整齐 |
| 综上所述 / 总而言之 / 值得注意的是 | 书面语套话，聊天里没人这么说 |
| 我理解你的困扰 / 我完全明白您的感受 | 空泛共情，没有任何信息量 |
| 这是一个很好的问题 | 客套，且回避了问题本身 |
| 希望这对您有帮助 / 如有其他问题请随时联系 | 客服模板 |
| 大量破折号串成的长句 | 一句里塞三四个 `——`，读起来像在朗读 |
| 每段都用「**结论：**」开头 | 结构化过度，像报告不像回话 |
| 「根据我的分析」/「经过仔细排查」 | 自我标榜，直接说发现了什么就行 |

### 3.3 对照示例

**❌ AI 味**

> 您好！非常感谢您提供的详细报告。经过仔细分析，我发现以下几个关键点：
> 首先，根据您提供的 StartupImpactReport，本模组的加载耗时为 64.7ms；
> 其次，该数值占总加载时间的 0.12%；
> 最后，综上所述，加载缓慢问题很可能并非由本模组引起。
> 希望以上分析对您有所帮助，如有其他问题欢迎随时反馈！

**✅ 人话**

> 谢谢你附这份报告，省得我自己猜。
>
> 我把里面的数字拉出来对了一下：「裸体评价更多看法 简体汉化」这一项是 64.7 ms，
> 占全部 234 个模组 52.3 秒的 0.12%。耗时前两名是 Exosuit Framework 10,448 ms
> 和 Humanoid Alien Races 10,104 ms，这俩加起来就 20 秒。
>
> 所以「十分钟缩到两分钟」我怀疑不是我们这边造成的 —— 64 毫秒怎么也不可能变成八分钟。
> 你删掉 opinionTexts 之后变快，更可能是那一次顺手也动了别的东西，或者磁盘缓存刚好生效了。
>
> 不过你说的方向本身没错。早期版本确实是一条条写进去的，那个是真的慢，
> 11 月 14 号的 v1.4.15 已经把架构换掉了。
>
> 不管怎样谢谢你把报告一起贴上来，这比一句「很慢」有用太多了。

### 3.4 几个具体手法

- **用对方给的数字**，而不是自己另算一套 —— 他一看就知道你真读了
- **说「我怀疑」而不是「可以确定」**，除非有铁证
- **承认对方说对的部分**（「你说的方向本身没错」），再指出数据对不上的地方
- **结尾给一条具体的下一步**（「升上来再测一次，把报告再贴上来」），不是「随时联系」
- **自嘲一句也行**（「省得我自己猜」），但别过头

## 四、回复里必须包含的信息

一条合格的回复，至少要有这三样：

1. **结论** —— 是什么问题 / 不是什么问题
2. **依据** —— 哪份日志、哪行报错、哪个反编译结果、哪个版本号
3. **下一步** —— 让对方做什么（升级 / 发日志 / 关掉某个开关），或者说明已经怎么改了

**不要只回「已修复」三个字** —— 对方不知道修的是不是他遇到的那个。

## 五、修完之后

- 改动要**同步到 README / About / 技术说明**（如果涉及对外可见的行为）
- 提交信息里写清**是谁报的、什么问题、怎么修的**
- 如果是别人报的 bug，在回复里可以提一句「这个已经进 vX.Y.Z 了」

## 六、检查清单

开工时：

- [ ] 两个仓库的 issue 全部看过
- [ ] 两个仓库的 PR 全部看过
- [ ] 工坊评论区扫过一眼
- [ ] 新 issue 已分类（能修 / 已解决 / 非本模组 / 待回测）

收工时：

- [ ] 这一轮新出现的问题都处理了
- [ ] 已解决的都回复并关闭了
- [ ] 没有「已回复但开着」的遗留
- [ ] 关闭理由填对了（`completed` / `not_planned`）
