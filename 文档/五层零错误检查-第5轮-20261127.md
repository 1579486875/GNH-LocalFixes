## 一、Harmony 幂等审查

### 1.1 判定标准

README 里那条铁律的原文：

> **Harmony 补丁安装必须幂等**：`CreateModClasses()` 自身带 `if (!runningModClasses.ContainsKey(type))` 守卫 ——
> 构造函数成功返回的模组不会被重复构造。真正的重入路径是：**构造函数抛异常** →
> 那条记录没写进 `runningModClasses` → 之后再次构造它。
> 因此**绝不能在 `Mod` 子类构造函数里做无保护的 `Harmony.PatchAll()`** ——
> Harmony 补丁是叠加的，失败后的重试会在同一方法上再套一层 prefix，
> 表现为「越操作越卡」直至卡死崩溃。所有补丁安装点都必须有静态标志守卫。

### 1.2 逐模组结果

| 模组 | 安装方式 | 守卫 | 判定 |
|---|---|---|---|
| **GNH-LocalFixes** | **不用 `PatchAll`**，改为逐条 `TryInstall` + `new Harmony().Patch(...)` | `private static bool installed`（源码里 285 处守卫相关行） | ✅ 最严谨 |
| **床铺增益** | `PatchAll` | `private static bool patchesApplied` | ✅ 见 1.3 |
| **米莉拉** | 逐条 `new Harmony(...).Patch(...)` | `private static bool installed` | ✅ |
| **RJW寄生虫** | 单次 `harmony.Patch(...)` | `[StaticConstructorOnStartup]`（CLR 保证只跑一次） | ✅ 见 1.4 |
| **Luxandra / S271 / Miho** | 无 C# 代码（纯 XML Def） | — | ✅ 无 Harmony 风险 |

### 1.3 床铺增益的守卫是全仓库最严谨的一份

```csharp
private static bool patchesApplied;

private static void ApplyHarmonyPatches()
{
    if (patchesApplied) return;          // 防重复

    try
    {
        new Harmony(HarmonyId).PatchAll(Assembly.GetExecutingAssembly());
        patchesApplied = true;
    }
    catch (System.Exception ex)
    {
        patchesApplied = true;           // ← 失败也立标志，这一点最关键
        Log.Warning("[UBFC] ...", ex);
    }
}
```

**「失败也立标志」不是偷懒，是刻意的取舍**，源码注释写得很清楚：

> `PatchAll` 是「一个补丁类一个补丁类地装」的，中途抛异常时前面几个很可能已经装上了。
> 如果这时留着 `false` 让下次再 `PatchAll` 一遍，那几个已装上的补丁就会被叠上第二层 ——
> 正是历史上「越操作越卡」的成因。两害相权取其轻：宁可这一局的保险丝没装上
> （核心功能完全不依赖 Harmony），也绝不让补丁叠层把游戏拖垮。

**这段注释本身也附了源码级依据** —— 指出 `runningModClasses[type] = Activator.CreateInstance(...)`
是「**先构造、后赋值**」，所以构造抛异常时字典里留不下记录。

### 1.4 RJW 寄生虫用 `[StaticConstructorOnStartup]`，本身就不需要守卫

```csharp
/// <summary>
/// 加载入口。<see cref="StaticConstructorOnStartup"/> 由 CLR 保证只跑一次，
/// 所以补丁不会像 Mod 子类构造函数那样被重复安装（重复安装会让补丁层层叠加）。
/// </summary>
[StaticConstructorOnStartup]
public static class Bootstrap
```

**这是正确的选择**：它没有 `Mod` 子类（不需要设置界面），
用 `[StaticConstructorOnStartup]` 就绕开了整类重入风险。

### 1.5 GNH-LocalFixes 的 `PatchAll` 只出现在归档目录

`grep PatchAll` 命中的 12 处**全部在 `临时-r346/src.pre-comments/`**（归档目录）。
而 csproj 的编译范围是：

```xml
<Compile Include="源码\**\*.cs" />
```

**只编 `源码/`，归档目录不参与编译** —— 已核对确认。

`源码/` 里的 `PatchAll` 字样全是**注释**（引述 Harmony 源码或历史说明），无实际调用。

### 2.3 `NMMOpinionsChineseUI` —— 发现并修掉一个真实隐患

原 csproj 写 `<LangVersion>latest</LangVersion>`，在 SDK 10 下解析为 **C# 14**。
而 GNH / 床铺 / 米莉拉三个工程都钉死 `9.0`。

改成 `9.0` 后重编译，**产物哈希 `52173a7129517332` 与已发布版本逐字节相同** ——

**反证已发布 DLL 本来就是 C# 9 产物**，`latest` 才是那个会随环境漂移的选项。

**已修**：两个 csproj 的 `LangVersion` 都改成 `9.0`（commit `256ddb7`）。

### 2.4 `GNH_NMM_Enhanced_ZH` —— 哈希不同，但语义等价

| | 旧（已发布） | 新（C# 9 重编译） |
|---|---|---|
| `typeCount` | 6 | 4 |
| `methodCount` | 14 | 12 |
| `namespaceCount` | 3 | 1 |

用 DecompilerServer 做两轮对比：

```
surface:  addedTypes 0 | removedTypes 0 | changedTypes 0 | unchangedTypes 2
deep:     addedTypes 0 | removedTypes 0 | changedTypes 0 | unchangedTypes 2
```

**业务类型 2 个、逐成员、逐方法体全部无差异。**

差异全部来自编译器生成的辅助类型（`<>c__DisplayClass` / `<PrivateImplementationDetails>`），
它们的数量随编译器版本与代码结构变化，不影响行为。

**处置**：把该 DLL 回滚为已发布版本，只保留 `LangVersion` 这个真实改进
（避免无意义的哈希变更打乱已发布产物的可追溯性）。
