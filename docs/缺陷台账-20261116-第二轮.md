## N-01 · NMM 汉化包的必要性复核 【✅ 仍必要 · 有量化证据】

模板 §1.4 的判据对汉化包是**「原模组自己带不带同一语言目录」**。本轮逐一取证：

| 被服务对象 | 自带中文？ | 判定 |
|---|---|---|
| `shark510.nuditymattersmoreopinions`（NMM opinions，1.6 时代的独立版） | **完全没有 `Languages` 目录** | **仍必要** |
| `dord.nuditymattersmore`（`RJW-功能-裸体评价` 目录，1.7 合并版） | **有** `1.7\Languages\ChineseSimplified`，442 文件 / 35 MB | **冗余候选** → 但见下 |

组合版自带中文的量化数据（本轮实测）：

| 目录 | 组合版自带 | 我们的包 |
|---|---:|---:|
| `Keyed` | 6 文件 / **477 键** | 28 文件 / **130,795 键** |
| `DefInjected`（各自 v1.7 树） | 436 文件 / **137,761 键** | 38 文件 / **1,226 键** |
| 根目录 `DefInjected` | — | 11 文件 / **16,706 键** |
| `OwnInjections`（整列表注入） | — | 47 文件 / **125,750 条** |

同名 9 个文件**内容全部不同**（不是同一份的副本）；组合版有 433 个我们没有的文件，
我们有 57 个它没有的。

**结论：两套是互补关系，不是重复。**

- 组合版强在**静态 `DefInjected` 键**（137,761 条）；
- 我们强在**正文 `Keyed`**（130,795 条）与**整列表注入**（125,750 条），这两块组合版几乎没有。

且 `About.xml` 的 `loadAfter` 含 `dord.nuditymattersmore` —— 我们排在组合版**之后**，
重叠的键由我们覆盖（设计意图：译文口径统一）。

**所以「原模组自带中文」这一条字面判据在这里会误判。** 判冗余必须按**键集合**算，不能按目录存在性算。

## P-01 · §1.3 性能：3 个热路径补丁的分配分析 【✅ 零分配】

按模板 §1.3 先分级（Harmony 目标方法的调用频率）：

| 目标方法 | 频率 | 危险度 | 我们的补丁 | 方法体分配 |
|---|---|---|---|---|
| `Thing.DynamicDrawPhase` | **每帧 × 每个可见 Thing** | 最危险 | `HarmonyFinalizer` | **0**（首行 `if (__exception == null) return null;` 即出） |
| `PawnRenderNodeWorker.ScaleFor` / `OffsetFor` | **每帧 × 每个 pawn** | 最危险 | `Prefix` + `Finalizer` | **0**（`Monitor.Enter` / `Monitor.IsEntered`+`Exit`） |
| `VerbProperties.AdjustedRange` | 每次开火判定 | 中 | `Prefix` | **0**（一次 null 比较 + 一次字段读） |
| `GenTypes.GetTypeInAnyAssembly` | 解析 XML 时每个类型名一次 | 中 | `Prefix` | **0**（两次字符串引用比较即返回） |
| `PatchOperation.Apply` / `Complete` | 启动期一次 | 一次性 | Prefix | 启动期，不敏感 |
| `LoadedModManager.LoadModXML` | 启动期一次 | 一次性 | Postfix | 同上 |
| `ModLister.HasActiveModWithName` | 查询 | 低 | Prefix | 小 |
| `PawnGenerator.GenerateNewPawnInternal` | 生成时 | 低 | Finalizer | 异常路径才有分配 |

**唯一的「每帧加锁」是 `SrceLibConcurrencyFix`**（`PawnRenderNodeWorker.ScaleFor`/`OffsetFor`）。
它是**修并发崩溃**的必要代价：不加锁时 SRCELib 的静态缓存被并发写，
日志每分钟成百上千条 `IndexOutOfRangeException`。

`Monitor` 在无竞争时是 thin lock（约 20 ns 量级），且这两个方法本来就要遍历渲染节点树。
**判为可接受**，记录在案；若日后实测掉帧，第一个该复查的就是这里。

## D-03 · 两个 DLL 的「是不是中文环境」兜底把非中文语言判成了中文 【P2 · ✅ 已修】

**发现方式**：反编译两个 DLL 的判据，与模板 §1.4 的「语言环境」维度对读。

**证据（v1.5.7 的 DLL 原文）**

```csharp
// NMMOpinionsChineseUI.Zh.IsChineseLanguage —— 末尾
// ⑥ 全都判不出来 → 兜底选择「替换」。
//    宁可误替换也不能漏：这本来就是中文汉化包，装它的都是中文玩家。
return true;

// GNH_NMM_Enhanced_ZH.EnhancedText.IsChinese —— 末尾
else
    v = true;                            // 兜底：宁可替换（与主补丁一致）
```

**谁被误伤**：判据输入是 `LanguageDatabase.activeLanguage`。`Russian (Русский)` /
`Japanese (日本語)` / `German (Deutsch)` / `French (Français)` / `Korean (한국어)` ……
在 ①②③④⑤ 全不命中 → 落到兜底 → **true** → 13 处替换全部生效。

后果：玩家装了本包、切到俄语，得到「俄语框架 + 中文界面与中文正文」的错乱组合。
**比全英文更难读**，而且看不出是哪个模组干的。

**为什么上一轮没修完**：R348 修的是「繁体被判成该汉化」（加了 ⑤ 的繁体排除），
但**兜底本身没动** —— 修了一个具体语言，没修根因。

**修法**（✅ 保意图，牺牲：无）

加一层**正向中文判据**，再把兜底改 false：

```
⑥ folderName 含 Chinese        → true
⑦ englishName 含 Chinese       → true
⑧ nativeName 含 中文 / 漢 / 汉  → true
⑨ 全不命中                      → false        ← 由 true 改来
```

关键点：改完之后**中文的识别面比改之前更宽**（原来 3 条路，现在 6 条），
所以「漏判导致满屏英文」这个原作者的担心不再成立 —— 这是敢改兜底的前提。

两个 DLL **必须同时改**，否则会出现「主补丁放行原文、增强界面却替换」的分叉。

**验证**

```
tools/audit-lang-detect.py  → 25 格全符合（主补丁 15 + 增强界面 10）
反编译 v1.5.8 的两个 DLL    → 末尾都是 return false / v = false，且正向判据在位
full-regression.py          → 9 / 9（新增闸门「语言判定判据表」）
```

判据全文见 `docs/语言判定-8场景.md`。
