## 二、三次自我纠错（本轮真正的收获）

### 错误 1：用 `#Strings` 堆做存在性判断 —— 误报 29 个「缺失」

**做法**：从 `Assembly-CSharp.dll` 的 `.NET metadata` 的 `#Strings` 堆提取所有标识符，
建成集合，检查目标是否在其中。

**结果**：`Def` / `Log` / `Verb` / `Pawn` / `Faction` / `Mathf` 全部 ❌
—— 但这几个是 RimWorld 最核心的类型，不可能不存在。

**根因**：`.NET metadata` 的 `#Strings` 堆**支持后缀折叠**（suffix folding）。
逐个验证发现：

```
Def      出现 4 次，但前=b't' 后=b's'  → 只是 ThingDefs / Defs 的一部分
Log      前=b'\x00' 后=b'1'            → 不是独立的 "Log"
Verb     前=b'e' 后=b's'               → 只是 Verbs 的一部分
Mathf    前=b'p' 后=b'\x00'            → 只是 xxxMathf 的一部分
```

**所以 `#Strings` 里根本没有独立的 `Def` 条目** —— 索引指向的是 `ThingDef` 里的 `D` 位置。

**结论：`#Strings` 不能用于类型存在性判断。**

### 错误 2：`get_types_in_namespace` 的输出被预算截断

**做法**：改用 DecompilerServer 的 `get_types_in_namespace(Verse)`，`limit: 10000`。

**结果**：返回体 **986 KB 被省略**，spill 文件里只有 **1,757 个** Verse 顶层类型，
但工具自己报 `totalEstimate: 3315`。

**根因**：MCP 输出有 1 MB 的字符预算上限（`budgetTruncated`）。
`limit: 10000` 并不能突破这个上限。

**所以「spill 里没有 = 不存在」这个推论不成立。**

### 错误 3：命名空间靠猜 —— `Faction` 不在 `Verse` 里

**做法**：用 `resolve_member_id("T:Verse.Faction")` 精确查。

**结果**：`type_not_found`。

**但 `Faction` 明明存在** —— 它在 **`RimWorld.Faction`**（GNH 源码里 `using RimWorld;`）。

同理：

```
T:Verse.Job    ❌ 找不到   →  实际是 T:Verse.AI.Job    ✅ 存在
T:Verse.Faction ❌ 找不到   →  实际是 T:RimWorld.Faction ✅ 存在
```

**所以「查不到」有三种可能**：类型不存在 / 命名空间猜错 / 工具输出截断。
**必须逐个排除才能下结论。**

## 四、能确认的结论

### 4.1 没有发现真正缺失的目标

所有标记为「缺失」的项，**都能归因到上面三个方法问题之一**：

| 「缺失」项 | 实际原因 |
|---|---|
| `Def` / `Log` / `Verb` / `Pawn` / `Mathf` | **错误 1**（`#Strings` 后缀折叠） |
| `CompAffectedByFacilities` / `Faction` / `Job` / `Need` / `Page_ModsConfig` / `PatchClassProcessor` / `UIRoot_Play` / `Verb_MeleeAttack` / `WorkshopItemHook` | **错误 2**（spill 截断）或 **错误 3**（命名空间） |
| `Pawn_HealthTracker.RestorePart` / `LongEventHandler:ExecuteToExecuteWhenFinished` / `Pawn_HealthTracker.pawn` / `Verse.AI.JobDriver.pawn` | **错误 2**（成员名不在被截断的那部分） |

### 4.2 补丁的失败是「自动让路」而非崩溃

GNH 的 `TryInstall` 结构本身保证这一点（源码 61 个文件通用）：

```csharp
private static void TryInstall(string toggleId, string name, Action install)
{
    if (!IsFixEnabled(toggleId)) { SafeLogMessage(...); return; }
    try
    {
        install();
        FixReport.MarkLoaded(toggleId);   // 记账：这次真装上了
    }
    catch (Exception ex)
    {
        SafeLogError("..." + name + ".Install() failed; that fix is NOT active this session: " + ex);
        FixReport.MarkFailed(toggleId);   // 记账：失败
    }
}
```

**每个补丁独立 try/catch + 独立开关 + 记账** —— 即使某个 `AccessTools` 探测失败，
也只影响那一条，**不会刷红字、不影响游戏启动**。

这也是为什么「目标签名核对」在 GNH 上**不是发布前的阻断项**：
它设计成「找不到就跳过」，而不是「找不到就崩」。

### 4.3 第三方模组的 20 个目标不需要核对

`BackstoryConstructor.*` / `NudityMattersMore.*` / `rjw.*` / `XmlExtensions.*` /
`SRAELib.*` / `RavenRace.*` / `Steamworks.SteamUser` / `ExtraWeaponComponent` ——
这些是**别的模组的类型**，本模组只在它们存在时才动手。
用 `AccessTools.TypeByName` 探测不到就 `return`，日志里记一句。

**核对它们「在不在 1.7 里」没有意义** —— 它们随第三方模组的版本变化。

## 五、正确的方法应该是什么（写给下次）

1. **不要用 `#Strings` 做存在性判断** —— 后缀折叠会让短名全部失踪
2. **不要用 `get_types_in_namespace` 做全量枚举** —— 大命名空间会撞 1 MB 预算
3. **命名空间必须从源码的 `using` 推导**，不能猜
4. **可靠做法**：
   - 单个类型：`resolve_member_id("T:Ns.Type")`（精确、无截断）
   - 单个成员：先 `resolve_member_id` 拿类型，再 `get_members_of_type` 看成员
   - 批量：**用编译器验证**（第 7 轮做的 1.7 编译实证比任何静态核对都可靠）

**第 7 轮的 1.7 编译实证已经覆盖了本层想验证的东西**：
如果某个 `AccessTools` 目标在 1.7 里不存在，**编译期不会报错**（因为是字符串/反射），
但**运行时会自动让路**。所以「编译通过 + 设计上自动让路」这两条合起来，
已经足以保证「不会因 API 变化而崩」。
