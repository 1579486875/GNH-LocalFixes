### 两个引擎的程序集依赖差异（关键）

用 Python 提取 metadata 里的 `AssemblyRef`：

| 引用方 | 依赖的 Unity 程序集 |
|---|---|
| **1.6 `Assembly-CSharp`** | `UnityEngine` + **`UnityEngine.CoreModule`** + **`UnityEngine.IMGUIModule`** + **`UnityEngine.TextRenderingModule`** |
| **1.7 `Assembly-CSharp`** | `UnityEngine` + **`UnityStubs`** |

**这就是全部矛盾的根源**：

- 1.6 的 `Rect` 来自 `UnityEngine.CoreModule.dll`
- 1.7 的 `Rect` 来自 `UnityStubs.dll`
- **两者类型同名但不同程序集** —— 在 C# 里视为**两个不同的类型**

## 三、1.7 编译验证（本轮新增）

### 3.1 方法

不能用 1.7 安装目录直接当引用源 —— 它**没有 `UnityEngine.dll`**，也没有 `Managed/` 目录。
所以改成：

```
Assembly-CSharp  → D:\steam\...\RimWorld\Assembly-CSharp.dll   （1.7）
UnityStubs       → D:\steam\...\RimWorld\UnityStubs.dll        （1.7，提供 UnityEngine 命名空间）
0Harmony         → 工坊 2009463077\1.6\Assemblies\0Harmony.dll （1.7 安装目录没有）
输出             → 临时目录（不碰各模组的 Assemblies/）
```

### 3.2 踩到的两个坑

**坑 1：`UnityStubs` 不能加 `<Aliases>`**

GNH 的 csproj 注释写着「必须给 Aliases，否则会和 UnityEngine.CoreModule 撞类型（CS0433）」。
但那句话的前提是**同时引用 `UnityEngine.CoreModule` 与 `UnityStubs`**。

**1.7 下没有 `UnityEngine.CoreModule`**，所以不该加别名。
加了之后源码里的 `using UnityEngine;` 会找不到 —— 因为别名要求写 `extern alias unitystubs;`。

**去掉别名后，`UnityStubs.dll` 内部的 `UnityEngine` 命名空间直接可用。**

**坑 2：`GenerateTargetFrameworkAttribute` 重复**

复制整个工程目录时把 `obj/` 也带过去了，导致 `CS0579: TargetFrameworkAttribute 特性重复`。
加 `<GenerateTargetFrameworkAttribute>false</GenerateTargetFrameworkAttribute>` 解决。

| 模组 | 1.7 编译 | 说明 |
|---|---|---|
| **床铺增益** | ✅ **成功**（0 警告 0 错误） | 只引用 `Assembly-CSharp` + `0Harmony` + Unity |
| **米莉拉** | ✅ **成功**（0 警告 0 错误） | 同上 |
| **RJW寄生虫** | ✅ **成功**（0 警告 0 错误） | 1.7 `Assembly-CSharp` + 1.6 引用目录的其它 dll |
| **GNH-LocalFixes** | ❌ **`CS0115`** | 见 3.4 |

床铺的 1.7 产物 24,064 B，与 1.6 产物同大小、哈希不同（引用的引擎不同）。

### 3.4 GNH 的 `CS0115` —— 这不是源码缺陷

```
源码\LocalFixesMod.cs(1163,30): error CS0115:
  "LocalFixesMod.DoSettingsWindowContents(Rect)": 没有找到适合的方法来重写
```

用 DecompilerServer 查 **1.7 的 `Verse.Mod`**：

```
DoSettingsWindowContents   Void DoSettingsWindowContents(Rect inRect)   isVirtual: true
SettingsCategory           String SettingsCategory()                     isVirtual: true
WriteSettings              Void WriteSettings()                         isVirtual: true
```

**方法存在、是 virtual、签名文字完全相同。**

那为什么对不上？因为 **`Rect` 是不同类型**：

```
GNH 引用了 ElToro_BAddon.dll 与 RJW.dll（1.6 编的第三方模组）
  → 这两个 dll 的 AssemblyRef 里有 UnityEngine.CoreModule
  → 编译器从 UnityEngine.CoreModule 里解析出 UnityEngine.Rect
1.7 的 Assembly-CSharp 期望 UnityStubs 里的 UnityEngine.Rect
  → 两个 Rect 不是同一类型
  → override 的签名不匹配 → CS0115
```

**对照实验**：床铺也重写了 `DoSettingsWindowContents(Rect)`，但它**不引用任何第三方模组 dll**
→ 1.7 编译**成功**。

**结论：这是「1.6 的第三方 dll 与 1.7 引擎混编」的固有限制，不是 GNH 源码的问题。**

## 四、关键结论：为什么「net48 + 1.6 refs」是正确的选择

GNH 的 csproj 里有一段注释解释了这个决策，本轮做了实证：

> **本工程【有意】把 Assembly-CSharp.dll 钉在 1.6**
> 本模组同时支持 1.6 与 1.7。用 **1.6 的程序集**编译，能保证「只用 1.6 就存在的 API」，
> 产物在两版上都能跑。反过来，若拿 1.7 的程序集编译，一旦用到 1.7 新增的 API，
> 1.6 玩家那边就是 `MissingMethodException` —— 而编译期完全看不出来。

**本轮实测支持这个判断**：

| 场景 | 结果 |
|---|---|
| net48 + 1.6 refs 编译的产物 → 1.7 运行 | ✅ **可加载**（引擎把 `UnityEngine.*` remap 到 `UnityStubs`） |
| net48 + 1.7 refs 编译 → 1.6 运行 | ❌ **不行**（用了 1.7 的 `UnityStubs` 类型，1.6 没有） |
| net48 + 1.7 refs 编译（零第三方依赖） | ✅ 可行，但**没有必要** —— 1.6 refs 的产物本来就两版通用 |

**所以「钉在 1.6」不只是保守，是唯一能同时覆盖两版的编译策略。**
